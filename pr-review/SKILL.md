# PR レビュー

## 目的

PR を「何をどう作るはずだったか（設計インプット）」「想定設計とズレていないか」「設計から逸脱・抜け・無駄・不揃い・無理・致命的バグがないか」の順に利用者と確認し、要対応の内容を修正コミット・TODO コメント・PR コメントで返す。細かい重箱の隅よりも設計の整合性を優先し、不要な説明を省いてテンポよく進める。

## 進め方

最初に workflow-base スキル（`../workflow-base/SKILL.md`）を読み込み、その共通ルールに従う。以下はこのスキル固有の手順である。

- フェーズ 0 と 1 の間は止まらない。フェーズ 1 の結果を出したところで最初に止まる。
- すでに利用者から要件・対応方針・気になっている点が十分な粒度で与えられている場合は、フェーズ 1 の確認を省いてフェーズ 2（ズレ確認）またはフェーズ 3（設計優先の評価）へ直接進んでよい。
- フェーズ 3 まではコードの変更と PR へのコメント投稿をしない。これらはフェーズ 4 でまとめて行う。PR の承認はしない。
- 答えが必要な質問として、PR を特定できないとき、設計インプットが不足しているとき、対応の分類が読み取れないときは、聞いてよい。

## 対応の分類

フェーズ 1 から 3 の間に利用者が対応を求めた内容を対応リストへ控え、フェーズ 4 まで保持する。

| 分類 | 利用者の言い方の例 | 対応 |
|---|---|---|
| こちらで修正 | 「これはこっちの対応で」「こっちで直す」「直接 push して」 | PR ブランチへ修正を直接コミットして push する |
| TODO コメント | 「これは TODO で」「あとでこっちでやる」 | 修正は後でこちらが行う前提で、この PR では TODO コメントだけをコミットして push する |
| 開発者へコメント | 「これは直してもらう」「指摘して」「コメントして」 | PR にコメントして開発者に直してもらう |

- 控えたら、番号、分類、内容を 1 行で復唱する。読み違いをその場で直せるようにするためである。
- 要対応なのに分類が読み取れないときは、その場で聞く。
- 分類の変更や取り消しを言われたら、対応リストへ反映する。

## フェーズ 0: 準備

利用者に確認せず、次を進める。

1. 対象の PR を特定する。番号や URL の指定がなければ、現在のブランチの PR を対象にする。特定できないときだけ、利用者に PR を聞いて止まる。
2. PR の情報を取得する。ホスティングサービスは `origin` の URL で判断する。
   - GitHub: `gh pr view <番号> --json number,title,body,url,baseRefName,headRefName,commits,files,closingIssuesReferences`
   - Azure DevOps: `az repos pr show --id <番号>`
3. PR のコードを参照できる状態にする。
   - 作業ツリーがきれいな場合: `gh pr checkout <番号>` または `az repos pr checkout --id <番号>`（他の作業ブランチを保ちたい場合は一時 worktree でもよい）
   - 未コミットの変更がある場合: 利用者の作業を壊さないよう、切り替えずに PR の head を fetch し、一時ディレクトリへ `git worktree add <パス> <ref>` で展開する。
4. base ブランチを fetch し、`git diff origin/<base>...HEAD` で PR の差分を確認する。
5. 関連する SDD 仕様書（`specs/` や `docs/` 等）および紐づくチケット（GitHub Issue / Azure DevOps Work Item）があれば取得する。

## フェーズ 1: 設計インプット

SDD の仕様書、関連チケットの対応方針、PR の説明から「要件」と「対応方針（想定設計）」を整理して提示する。

- 仕様書やチケットが存在しない、または古い・曖昧で対応方針が読み取れない場合は、その旨を明示して利用者から要件と対応方針を入力してもらう。
- 利用者が事前に気にしている点（気になる差分、配置、抜け漏れの疑いなど）があれば、あわせて受け取る。

次の形式で出力して止まる。

```markdown
## フェーズ 1: 設計インプット

### <PR の番号とタイトル>

- **情報源**: <仕様書パス / チケット番号 / PR 説明。なければ「なし」>
- **要件**: <何ができるようになるか>
- **対応方針（想定設計）**: <どう実装する前提か>
- **不足・古い可能性がある点**: <なければこの行を書かない>
```

## フェーズ 2: 想定設計とのズレ確認（必要なものに限る）

実装（差分と関連する既存コード）を読み、フェーズ 1 の想定設計とのズレがあれば説明する。

- **設計確認が必要なものに限って説明する。** 設計の余地がなく想定通りで不確実性がない箇所は説明や図を省く。
- 処理の流れやクラス責務にズレや複雑さがある箇所だけ、必要に応じて workflow-base のスイムレーン図や要点箇条書きで示す。
- 想定設計とのズレが特になければ「想定設計との大きなズレはありません」と短く伝えてフェーズ 3 へ進めてよい（ズレがあるときだけ止まって認識を合わせる）。

## フェーズ 3: 設計優先の評価

フェーズ 1 の想定設計、共通コーディングルール（[../workflow-base/references/coding-rules.md](../workflow-base/references/coding-rules.md)）、および評価観点表（[references/review-criteria.md](references/review-criteria.md)）を基準に実装を評価する。

- 設計の整合性を最優先し、細かいバグや好みの指摘は省く。バグは致命的なもの（ビルド不能、実行時例外、データ破損など）だけを拾う。
- 差分の外（既存の類似実装、enum 分岐、ジェネレーター、ファクトリ、登録箇所、呼び出し元、テスト）も必ず読み、コードで裏付けが取れたものだけを指摘する。
- 利用者がフェーズ 1 で挙げた気になっている点がある場合は、最初にその回答を明示する。

重要度（高・中）ごとに整理し、問題の箇所へ workflow-base の書式でリンクを付けて出力し、止まる。

```markdown
## フェーズ 3: 設計優先の評価

### 気にされていた点の確認
（該当がある場合のみ）

### 指摘一覧

#### 1. [高] <観点>: <問題の要約>

[path/to/file:42](path/to/file:42)

- 問題: <想定設計や既存コードに対して何がどう問題か>
- 根拠: <コードのどこからそう言えるか>
- 修正案: <どう直すか>
```

指摘がなければ、確認した範囲とともにそう伝える。

## フェーズ 4: アクション（FB）

フェーズ 3 の指摘および利用者が追加した項目について、対応の分類（「こちらで修正」「TODO コメント」「開発者へコメント」）が決まったら実行する。対応リストが空なら「終了」へ進む。

### 1. 対応一覧の確認

次の形式で全件を出して止まる（すでに利用者から分類と実行指示が明確に出ている場合はそのまま実行へ進んでよい）。

```markdown
## フェーズ 4: アクション

### こちらで修正
1. <修正内容> [path/to/file:42](path/to/file:42)

### TODO コメント
1. TODO(<作業者名>): <あとで対応する内容> [path/to/file:42](path/to/file:42)

### 開発者へコメント
1. <コメント本文> [path/to/file:42](path/to/file:42)
```

### 2. PR ブランチへコミットする

1. PR ブランチの最新 head に合わせる。レビュー後に head が進んでいたら、一覧の内容が今も当てはまるかを確かめる。
2. 「こちらで修正」を論理的な単位でコミットを分けて修正し、関連するテストかビルドを確認してコミットする。
3. 「TODO コメント」を該当行の直前へ追加し、`TODO(<作業者名>): <あとで対応する内容>` の形式でコミットする（作業者名は `git config user.name` の値）。
4. 全件のコミットが終わったら `git push` で PR ブランチへ反映する。force push はしない。

テストが通らないときや push が拒否されたときは、そこで止めて報告する。

### 3. PR にコメントする

開発者へのコメントを 1 件ずつ、該当するファイルの行へ投稿する。

- 修正で行番号がずれるため、位置は push 後の最新コミットで取り直す。
- 本文は平易な日本語で、何が問題でどう直すかを 1〜2 文のプレーンテキストで書く（Markdown の見出し・箇条書き・装飾は使わない）。
- 柔らかい言い回し（「〜していただけますか」「〜するのはいかがでしょうか」）にする。
- 投稿コマンド:
  - GitHub: `gh api repos/{owner}/{repo}/pulls/<番号>/comments -f commit_id=<最新コミットの SHA> -f path=<パス> -F line=<行番号> -f side=RIGHT -f body=<本文>`
  - Azure DevOps: `az devops invoke --area git --resource pullRequestThreads --http-method POST`（日本語を含む JSON は `ensure_ascii=True` でエスケープして `--in-file` で渡す）

## 観点表を育てる手順

レビューの中で既存の観点表（[references/review-criteria.md](references/review-criteria.md)）にない有効な観点やチェック項目が見つかったら、次の手順で追記する。

1. **追記するとき**: フェーズ 3 の指摘やフェーズ 4 のアクションで利用者に採用された新しい観点があるとき。
2. **追記する場所**: [references/review-criteria.md](references/review-criteria.md) の該当カテゴリの末尾に 1 行で追記する。
3. **反映のしかた**: この `SKILL.md` がある Git リポジトリの既定ブランチを `git pull --ff-only` で最新化し、`pr-review/references/review-criteria.md` だけをコミットして `git push` する。レビュー対象のリポジトリのブランチには含めない。
4. **反映できないとき**: リポジトリでない、未コミットの変更がある、push が拒否されたなどの場合は、追記する内容を利用者に報告して作業を続ける。

## 終了

作成したコミットと投稿したコメントを報告する。一時 worktree を使った場合は、不要であれば削除する。
