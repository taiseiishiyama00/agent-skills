# PR レビュー

## 目的

PR を「何が変わったか」「どう作られたか」「コードに問題はないか」の順に、利用者と認識を合わせながら確認し、要対応の内容を修正のコミットと PR コメントで返す。全部を一度に出すと読み切れず、前提がずれたまま指摘だけが並ぶため、1 回の応答で 1 フェーズだけ出す。

## 進め方

最初に workflow-base スキル（`../workflow-base/SKILL.md`）を読み込み、その共通ルールに従う。以下はこのスキル固有の手順である。

- フェーズ 0 と 1 の間は止まらない。フェーズ 1 の結果を出したところで最初に止まる。
- 先のフェーズの内容は先に出さない。フェーズ 1 や 2 の調査中に見つけたバグは控えておき、フェーズ 3 で指摘する。
- フェーズ 3 まではコードの変更と PR へのコメント投稿をしない。これらはフェーズ 4 でまとめて行う。PR の承認はしない。
- 答えが必要な質問として、PR を特定できないときと、対応の分類が読み取れないときは、選択肢で聞いてよい。

## 対応の分類

フェーズ 1 から 3 の間に利用者が対応を求めた内容を対応リストへ控え、フェーズ 4 まで保持する。

| 分類 | 利用者の言い方の例 | 対応 |
|---|---|---|
| こちらで修正 | 「これはこっちの対応で」「こっちで直す」 | PR ブランチへ修正を直接コミットして push する |
| TODO コメント | 「これは TODO で」「あとでこっちでやる」 | 修正は後でこちらが行う前提で、この PR では TODO コメントだけをコミットして push する |
| 開発者へコメント | 「これは直してもらう」「指摘して」 | PR にコメントして開発者に直してもらう |

- 控えたら、番号、分類、内容を 1 行で復唱する。読み違いをその場で直せるようにするためである。
- 要対応なのに分類が読み取れないときは、その場で聞く。
- 分類の変更や取り消しを言われたら、対応リストへ反映する。

## フェーズ 0: 準備

利用者に確認せず、次を進める。

1. 対象の PR を特定する。番号や URL の指定がなければ、現在のブランチの PR を対象にする。特定できないときだけ、利用者に PR を聞いて止まる。
2. PR の情報を取得する。ホスティングサービスは `origin` の URL で判断する。
   - GitHub: `gh pr view <番号> --json number,title,body,url,baseRefName,headRefName,commits,files,closingIssuesReferences`
   - Azure DevOps: `az repos pr show --id <番号>`
3. PR のコードをチェックアウトする。
   - 作業ツリーがきれいな場合: `gh pr checkout <番号>` または `az repos pr checkout --id <番号>`
   - 未コミットの変更がある場合: 利用者の作業を壊さないよう、切り替えずに PR の head を fetch し、スクラッチパッドなどの一時ディレクトリへ `git worktree add --detach <パス> FETCH_HEAD` で展開する。GitHub の ref は `pull/<番号>/head`、Azure DevOps の ref は PR の source branch。
4. base ブランチを fetch し、`git diff origin/<base>...HEAD` で PR の差分を確認する。

## フェーズ 1: ユーザーストーリーベースで差分を整理する

差分を workflow-base のユーザーストーリーの書式でまとめる。

- 変更前の体験を書くために、差分だけでなく base 側のコードも読む。
- PR の説明は手がかりとして使い、内容は差分で確かめる。説明と差分が食い違うときは、その点を明記する。

次の形式で出力して止まる。

```markdown
## <PR の番号とタイトル>

1. **<ストーリー名>**（<主体>）: <「にした」で結んだストーリー>
2. **<ストーリー名>**（<主体>）: <「にした」で結んだストーリー>

ユーザー体験が変わらない変更: <リファクタリング、テスト、CI など。なければこの行を書かない>
```

## フェーズ 2: 設計を確認する

フェーズ 1 の順に、ユーザーストーリーごとの処理の流れを workflow-base のスイムレーンで描く。今回の変更部分は、PR で変更した部分とする。

- 図の下に、このストーリーでの各クラスの責務の変化と、設計上の懸念（責務の置き場所、依存の向き、既存の仕組みとの二重化）を短く書く。コードの書き方の指摘はフェーズ 3 に回す。
- ユーザー体験が変わらない変更は、設計に影響があるときだけ最後に加える。

全ストーリーを出したら止まる。

## フェーズ 3: コードを確認する

次の観点で問題を探す。

- バグ: 誤った動作、異常系の漏れ、データの破損や不整合
- 無駄: 重複、既存機能の再実装、使われていないコード、不要な処理
- 無理のあるコーディング: 仕組みに逆らった実装、過剰な複雑さ、脆い前提

差分の外も読む。重複や呼び出し元への影響は差分だけでは見つからないため、呼び出し元、似た処理を持つ既存コード、テストを確認する。

指摘を出す前に全件を洗い出し、コードで裏付けが取れたものだけを重要度順に並べる。好みや推測は指摘に含めない。

| 重要度 | 基準 |
|---|---|
| 高 | ユーザーやデータに実害が出る |
| 中 | 今は動くが、性能、変更、運用で問題になる |
| 低 | 動作に影響しないが、読みにくさや無駄がある |

最初に重要度別の件数を 1 行で示してから、全件を次の形式で出して止まる。

```markdown
### 1. [高] バグ: <問題の要約>

[path/to/file:42](path/to/file:42)

- 問題: <どの入力や状態で何が起きるか>
- 根拠: <コードのどこからそう言えるか>
- 修正案: <どう直すか>
```

各指摘には、workflow-base の書式で、問題の箇所へのリンクを付ける。

指摘がなければ、確認した範囲とともにそう伝える。

## フェーズ 4: FB

フェーズ 3 の確認が終わったら開始する。対応リストが空なら「終了」へ進む。

### 1. 一覧を出す

次の形式で全件を出して止まる。push とコメントは開発者の目に触れるため、ここで止める。「次」と入力されたら、以降は止まらず最後まで進める。

```markdown
## こちらで修正

1. <修正内容> [path/to/file:42](path/to/file:42)

## TODO コメント

1. TODO(<作業者名>): <あとで対応する内容> [path/to/file:42](path/to/file:42)

## 開発者へコメント

1. <コメント本文> [path/to/file:42](path/to/file:42)

## 未分類

- <フェーズ 3 の指摘のうち分類されていないもの。なければこの見出しを書かない>
```

未分類の指摘には対応しない。利用者が分類したら対応リストへ加える。

### 2. PR ブランチへコミットする

1. チェックアウト先で `gh pr checkout <番号>` または `az repos pr checkout --id <番号>` を実行し、PR ブランチの最新の head に合わせる。レビュー後に head が進んでいたら、一覧の内容が今も当てはまるかを確かめる。
2. 「こちらで修正」を一覧の順に 1 項目ずつ修正し、関連するテストかビルドを確認して、1 項目 1 コミットでコミットする。コミットメッセージはリポジトリの慣例に合わせる。
3. 「TODO コメント」を一覧の順に、該当する行の直前へ追加し、1 項目 1 コミットでコミットする。
   - 書式は `TODO(<作業者名>): <あとで対応する内容>` とし、コメント記法は対象の言語に合わせる。リポジトリに TODO の書式があればそれに従い、作業者名は必ず入れる。
   - 作業者名は `git config user.name` の値にする。利用者が別の人を指定したら、その人の名前にする。
4. 全件のコミットが終わったら `git push` で PR ブランチへ反映する。force push はしない。

テストが通らないときや push が拒否されたときは、そこで止めて報告する。

### 3. PR にコメントする

開発者へのコメントを 1 件ずつ、該当するファイルの行へ投稿する。全体へのコメントは投稿しない。開発者が直す場所をすぐ開けるようにするためである。

- 修正で行番号がずれるため、位置は push 後の最新コミットで取り直す。
- 問題の箇所が PR の差分の外にあるときや、設計への指摘で特定の行がないときは、差分の中で最も関係する行に付ける。
- 本文は平易な日本語で、何が問題でどう直すかを 1〜2 文で書く。Markdown の見出し、箇条書き、装飾、コードブロックは使わず、プレーンテキストにする。
- 開発者が受け取りやすいよう、柔らかい言い回しにする。「〜してください」ではなく「〜していただけますか」「〜するのはいかがでしょうか」のような依頼や提案の形にし、「〜はおかしい」「〜すべき」のような決めつけや命令は使わない。

例:

```text
在庫が 0 のときも注文が確定してしまうようです。確定の前に在庫を確認していただけますか。
```

投稿のコマンドは次のとおり。

- GitHub: `gh api repos/{owner}/{repo}/pulls/<番号>/comments -f commit_id=<最新コミットの SHA> -f path=<パス> -F line=<行番号> -f side=RIGHT -f body=<本文>`
- Azure DevOps: `az devops invoke --area git --resource pullRequestThreads --http-method POST` でスレッドを作り、`threadContext` の `filePath`、`rightFileStart`、`rightFileEnd` で位置を指定する。

## 終了

作成したコミットと投稿したコメントの URL を報告する。一時 worktree を使った場合は、変更がないことを確認して削除する。
