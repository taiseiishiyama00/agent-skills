# 資料作成ワークフロー

## 目的

資料を「どの形式で出すか」「何を根拠に何を伝えるか」「どういう順で構成するか」を利用者と合意してから作り始める。材料が足りないまま書き始めたり、全ページを一度に作ったりすると手戻りが大きくなるため、構成をテキストで固めたうえで、1 枚（または 1 章）ずつ作成とレビューを繰り返して仕上げる。

## 進め方

```text
フェーズ 1（フォーマット決定）→ フェーズ 2（材料収集）→ フェーズ 3（構成案作成）
ページ・章ごとに繰り返す
    フェーズ 4（1 枚 / 1 章ずつ作成・レビュー）
フェーズ 5（全体確認・仕上げ）
```

最初に workflow-base スキル（`../workflow-base/SKILL.md`）を読み込み、その共通ルールに従う。以下はこのスキル固有の手順である。

- フェーズ 1〜3 とフェーズ 5 は 1 フェーズごとに止まる。フェーズ 4 の止まる単位は **1 枚（スライド型は 1 スライド、文書型は 1 章または 1 セクション）** とし、利用者が明示的にまとめて作成するよう指示しない限り、先のページ・章を先回りして作らない。
- フェーズ 4 では、フェーズ見出しの次に `## スライド 1/7: <タイトル>`（文書型は `## 章 1/5: <章タイトル>`）のように対象の番号と位置を示す。次に進む先も「スライド 2/7: <次のタイトル> に進みます。」のように番号とタイトルを添えて書く。
- 答えが必要な質問として、フェーズ 1 のフォーマット・型・出力先の確認、フェーズ 2 の報告種別や不足情報の確認、既存ファイルの上書き可否は、選択肢で聞いてよい。
- 後のフェーズで、合意済みのフォーマット、収集した事実、構成案を変える必要が出たら、勝手に変えずに理由を示して確認する。
- 足りない数値・事実・決定事項を推測や架空の例で埋めない。仮置きが必要なときは利用者の合意を得て `[仮]` と明記する。

## フェーズ 1: フォーマット決定

資料の出力形式と作成粒度の前提を揃える。利用者の初回依頼にフォーマットが含まれている場合も、資料の型・出力先・テンプレート有無を確定させるためこのフェーズで一度止まる。

1. **フォーマット**: PowerPoint（`.pptx`）、PDF（`.pdf`）、Markdown（`.md`）、HTML（`.html`）など、どの形式で出力するかを確認する。未定の場合は用途に合う選択肢と特徴を挙げて聞く。
2. **資料の型（レビューの単位）**: フォーマットに応じて、構成・作成・レビューの単位を決める。
   - **スライド型**: PowerPoint、スライド PDF、Marp などのスライド Markdown、HTML スライド → **1 スライド単位** で進める。
   - **文書型**: 通常の Markdown、文書 HTML、レポート PDF → **1 章（または 1 セクション／1 ページ）単位** で進める。
   - PDF・Markdown・HTML は両方の型を取り得るため、フォーマットと同時に型も確認する。
3. **出力先と参照資料**: 保存先のファイルパス（出力先に既存ファイルがある場合は上書きするか別名にするか）、既存テンプレートやデザイン指定、手元にある参照資料（メモ、ログ、コード、データ等）の有無を確認する。

フォーマット・型・出力先が決まったら、次の形式でまとめて出して止まる。

```markdown
## フェーズ 1: フォーマット決定

- フォーマット: <PowerPoint (.pptx) / PDF (.pdf) / Markdown (.md) / HTML (.html)>
- 資料の型: <スライド型（1 スライド単位） / 文書型（1 章単位）>
- 出力先: <ファイルパス>
- テンプレート・参照資料: <パスや指定、なければ「なし」>

問題なければ「次」と入力してください（あわせて、今回伝えたいこと・やりたいことや手元のメモがあれば教えてください）。フェーズ 2: 材料収集に進みます。
```

すでに初回依頼でメモや参照資料が渡されている場合は、その旨を添えて確認し、「次」の入力後にフェーズ 2 へ進む。

## フェーズ 2: 材料収集

利用者が出した「やりたいこと・伝えたいこと」をフレームワークで整理し、不足している情報や根拠を聞き出して材料を揃える。

### 1. 手元資料の把握と種別の選定

1. 利用者のメモや要望を受け取り、参照ファイル・リポジトリ・ログ等のパスが示されていれば先に読み込んで事実関係を把握する。手元の資料やコードを読めば分かることを利用者に聞き返さない。
2. フレームワーク・観点表（[references/frameworks.md](references/frameworks.md)）を読み込み、共通フレームワークと該当する資料の種別を選ぶ。複数の種別にまたがる場合は、該当するすべての種別を使う。
3. 観点表のどの種別・観点にも当てはまらない要素がある場合は、新しい名前を付け、「`<名前>（表にない）`」と書く。

### 2. 不足情報の洗い出し（揃うまで繰り返す）

集まった情報を共通フレームワークの軸と種別ごとの観点へ当てはめ、事実（数値・日時・一次情報）と解釈・見解を分けて整理する。足りない情報や根拠が曖昧な箇所を洗い出し、次の形式で出して止まる。

```markdown
## フェーズ 2: 材料収集

種別: <選んだ種別>

| 観点 | 集まった材料 | 状態 |
|---|---|---|
| <観点名> | <読み取れた事実・前提・解釈> | 済 |
| <観点名> | <不足している点や要確認の点> | 不足 |

不足している情報・確認したいこと:

1. <観点>: <補足してほしい具体的な質問>
2. <観点>: <補足してほしい具体的な質問>

不足している情報を教えてください（不要な観点は「対象外」と伝えてください）。
```

すべての観点が「済」「対象外」、または利用者合意済みの「`[仮]`」で埋まるまで繰り返す。

### 3. 材料をまとめる

すべての観点が埋まったら、収集した材料の全件を次の形式で出して止まる。

```markdown
## フェーズ 2: 材料収集

種別: <選んだ種別>

### 前提・ゴール
- 宛先・場面: <誰に・どの場で>
- 求める反応: <共有 / 判断・承認 / 相談 など>
- 全体結論: <1〜2 文の結論>

### 整理した材料
| 観点 | 内容（事実と解釈を分けて記載） |
|---|---|
| <観点名> | <確定した材料> |

対象外: <対象外とした観点。なければこの行を書かない>

問題なければ「次」と入力してください。フェーズ 3: 構成案作成に進みます。
```

「次」と入力されたら、表にない種別や観点を [references/frameworks.md](references/frameworks.md) へ追記してから、フェーズ 3 へ進む。

### フレームワーク表を育てる

フレームワーク・観点表（[references/frameworks.md](references/frameworks.md)）は、使うたびに育てていく部分である。表にない種別や観点が採用されたら、次の手順で追記する。

1. この `SKILL.md` があるディレクトリの Git リポジトリで、既定ブランチを pull する。
2. [references/frameworks.md](references/frameworks.md) の該当箇所に観点または種別の行を追記する。
3. `references/frameworks.md` だけを、`doc-creation のフレームワーク表に<種別または観点>を追加` のようなメッセージでコミットし、既定ブランチへ push する。資料を作成している作業中のリポジトリや別ブランチには含めない。
4. リポジトリでない、未コミットの変更がある、push が拒否されたなどで反映できないときは、追記する内容を利用者に報告して、ワークフローを続ける。

## フェーズ 3: 構成案作成

確定した材料と、フェーズ 1 のフォーマット・型に合わせて、テキストベースで全体のページ構成または章構成を設計する。

- 並び順は [references/frameworks.md](references/frameworks.md) の「骨格の流れ」を基準にし、結論やサマリを前に置いてから事実・考察・次の一手へつなげる。
- **1 枚（1 章）= 1 メッセージ** を徹底し、1 ページに複数の論点を詰め込まない。見出しとキーメッセージだけで流れが追える状態にする。
- 各ページ・章に使う材料と、適した見せ方（箇条書き、表、グラフ、図解、地の文など）を指定する。

次の形式で全件を出して止まる。

```markdown
## フェーズ 3: 構成案作成

フォーマット: <フォーマット>（<スライド型 / 文書型>）
全体構成: 全 <N> 枚（文書型は 全 <N> 章）

### 1. <ページ・章のタイトル>
- 役割: <表紙 / 結論サマリ / 事実・根拠 / 課題と対策 / ネクストアクション 等>
- キーメッセージ: <この 1 枚・1 章で伝えたいこと（1 文）>
- 入れる材料: <使用する事実・数値・考察>
- 見せ方: <箇条書き / 表 / グラフ / 図解 / 地の文 等>

...

構成の順番、枚数や章立て、各ページのメッセージに直したい点があれば教えてください。
問題なければ「次」と入力してください。フェーズ 4: 資料作成（スライド 1/N: <タイトル>）に進みます。
```

## フェーズ 4: 資料作成（1 枚 / 1 章ずつ作成・レビュー）

構成案の順に、**1 回の応答で 1 枚（または 1 章）だけ** 作成して出力ファイルへ反映し、レビューを受けてから次へ進む。

### 1. 実ファイル生成の方針（1 枚目の前に揃える）

- 1 枚目（1 章目）を作成する際、フォーマットに応じた全体のデザイン方針・書式（配色、フォント、レイアウト枠、Markdown の見出し粒度やフロントマター等）を定め、作成内容とあわせて示す。
- PowerPoint（`.pptx`）や PDF（`.pdf`）などを生成する際、環境に `pptx` や `pdf` などの専用スキルがある場合は、その手順・制約・バリデーションに従って実ファイルを生成する。
- 専用スキルがない環境でも利用可能なライブラリや変換手段で実ファイルを生成する。環境上の制約で実ファイルを直接生成できない場合は、勝手にテキスト出力だけで済ませず、代替の生成方法を利用者に確認して決める。

### 2. 1 枚ごとの提示とレビューの聞き方

対象の 1 枚（1 章）を作成・更新したら、次の形式で出して止まる。

```markdown
## フェーズ 4: 資料作成
## スライド 1/N: <タイトル>

- 更新ファイル: [<ファイル名>](<ファイルパス>)
- 作成した内容:
  <Markdown なら該当ページ・章の全文。PPTX / HTML / PDF なら記載した見出し・本文・図表・話者メモとレイアウト構成。画像プレビューを生成できる環境では視覚確認の結果や画像パスも添える>
- 狙い・工夫点: <なぜこの配置・図表・表現にしたかを 1〜2 行>
- 確認してほしい点:
  - 事実・数値・結論に意図とのずれや過不足はないか
  - 情報量・表現・トーンが読み手に合っているか
  - レイアウトや図解・文章で直したい点はないか

修正したい点があれば教えてください。問題なければ「次」と入力してください。スライド 2/N: <次のタイトル> に進みます。
```

- 文書型の場合は `## 章 1/N: <タイトル>` とし、進み先も「章 2/N: <次のタイトル> に進みます。」と書く。
- 最後の 1 枚（`N/N`）を出したときは、進み先を「フェーズ 5: 全体確認・仕上げに進みます。」とする。
- 利用者からフィードバックが来たら、指摘されたページ（前のページへの戻りを含む）を修正して出力ファイルを更新し、同じページ見出しを付けて再度提示して止まる。
- 「次」と入力されたら次のページ・章へ進み、全ページ・全章を終えたらフェーズ 5 へ進む。

## フェーズ 5: 全体確認・仕上げ

全ページ・全章が揃ったら、最終出力ファイルを通しで確認して仕上げる。

1. **構成と内容の整合確認**: 表紙・目次・ページ番号・章番号の連番、構成案と材料表との突合（数値の食い違い、根拠のない断定、事実と解釈の混同がないか）、誤字脱字や表記の不整合を確認する。
2. **フォーマット固有の検証**:
   - PowerPoint（`.pptx`）: 構造検証（専用スキルの検証スクリプトがあれば実行）と全スライドの視覚確認（文字切れ・重なり・余白崩れがないか）を行う。
   - PDF（`.pdf`）: 改ページ位置・余白・文字切れ・ページ番号を確認する。
   - HTML（`.html`）: 表示崩れ・リンク・レスポンシブ表示を確認する。
   - Markdown（`.md`）: 見出し階層・表・コードブロック・リンク・ページ区切り（`---`）を確認する。
3. 検証で修正した点があれば内容を明記し、最終成果物へのリンクとサマリを出して完了する。

```markdown
## フェーズ 5: 全体確認・仕上げ

- 出力ファイル: [<ファイル名>](<ファイルパス>)
- フォーマット・規模: <フォーマット>（<スライド型 / 文書型>・全 <N> 枚 / 全 <N> 章）
- 確認結果: <通し確認・レイアウト検証で問題なかったこと、および微調整した内容>
```
