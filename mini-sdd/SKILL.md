# ミニ SDD

## 目的

実装を「何を作るか」「どう作るか」「何で確かめるか」を利用者と合意してから進める。合意のないまま書いたコードは手戻りになるため、各フェーズの結果を利用者に確認してから次へ進む。

## 進め方

フェーズ 2 から 4 はユーザーストーリーごとに繰り返し、その中でフェーズ 4 はテストごとに繰り返す。1 件のストーリーを設計からテストの実装まで終えてから次のストーリーへ進むことで、前のストーリーで作ったコードを次の設計の前提にできる。

```text
フェーズ 0 → フェーズ 1
ユーザーストーリーごとに繰り返す
    フェーズ 2 → フェーズ 3
    テストごとに繰り返す
        フェーズ 4
フェーズ 5
```

最初に workflow-base スキル（`../workflow-base/SKILL.md`）を読み込み、その共通ルールに従う。以下はこのスキル固有の手順である。

- フェーズ 0 と 1 の間は止まらない。フェーズ 1 の最初の質問を出したところで最初に止まる。
- フェーズ 2 と 3 で出すのは、対象のユーザーストーリー 1 件分である。フェーズ 4 は、テスト 1 件ごとに止まる。
- フェーズ 2 から 4 の出力の先頭には、`## ストーリー 1/3: <ストーリー名>` のように対象のストーリーを示す。
- 答えが必要な質問として、フェーズ 0 の未コミット変更の扱いとフェーズ 1 の質問は、選択肢で聞いてよい。
- 後のフェーズで、合意済みのユーザーストーリー、設計、テスト一覧を変える必要が出たら、勝手に変えずに理由を示して確認する。

## フェーズ 0: チェックアウト

利用者に確認せず、次を進める。

1. 未コミットの変更があれば、作業を壊さないよう、何もせずに利用者へ扱いを聞いて止まる。
2. 既定ブランチを fetch し、最新の既定ブランチから作業ブランチを作って切り替える。ブランチ名はリポジトリの慣例に合わせ、慣例がなければ `feature/<依頼内容の短い英語名>` にする。
3. 依頼に関係するコード、テスト、issue やチケットを読み、現在の動きをつかむ。コードを読めば分かることを利用者に聞かないためである。

## フェーズ 1: ユーザーストーリーの定義

利用者に質問して、ユーザーストーリーを固める。

- 質問は 1 回に 3 つまでにし、実装への影響が大きいものから聞く。答えに応じて次の質問を決める。
- 質問には、コードから読み取った現状と、推奨する答えを添える。利用者が選ぶだけで答えられるようにするためである。

固まったら、workflow-base のユーザーストーリーの書式に受け入れ条件を付けた次の形式で、全件を出して止まる。

```markdown
1. **<ストーリー名>**: <「にする」で結んだストーリー>
   - 受け入れ条件: <満たすべき条件>
   - 受け入れ条件: <満たすべき条件>
```

## フェーズ 2: 設計

対象のユーザーストーリーについて、次の 2 つを設計して止まる。前のストーリーで作ったクラスは前提として使う。

### コントラクト

ユーザーとの接点を決める。接点の種類に応じて、次を書く。

| 接点 | 書くこと |
|---|---|
| 画面 | 画面、操作、表示する内容、エラー時の表示 |
| API | メソッドとパス、リクエスト、レスポンス、エラー時の応答 |
| その他（CLI、イベント、ファイルなど） | 入力、出力、エラー時の動き |

### クラス設計

1. workflow-base のスイムレーンで処理の流れを描く。今回の変更部分は、このストーリーで変更する部分とする。
2. 図の下に、新規または変更するクラスを次の形式で並べる。既存の似たコードの構成と命名に合わせる。

```markdown
| クラス | 新規/変更 | 責務 | 公開メソッド |
|---|---|---|---|
| OrderService | 変更 | 注文の確定を判断する | `Confirm(order)` |
```

## フェーズ 3: テスト設計

対象のユーザーストーリーの単体テストの一覧を作る。全件を出して止まる。

- このストーリーの全ての受け入れ条件と、フェーズ 2 の公開メソッドの正常系と異常系を、いずれかのテストで確かめる。
- 実装しやすい順に並べる。単純なケースから始め、前のテストの実装を土台に次へ進めるようにするためである。
- テスト名はリポジトリの慣例に合わせる。

```markdown
| # | 対象 | テスト名 | 条件 | 期待する結果 | 受け入れ条件 |
|---|---|---|---|---|---|
| 1 | OrderService.Confirm | 在庫があれば注文を確定する | 在庫数 1 | 確定済みになる | 1-1 |
```

## フェーズ 4: TDD

対象のユーザーストーリーのテスト一覧の順に、1 件ずつ red、green、refactor を進める。

1. Red: テストを 1 件だけ書いて実行し、期待どおりの理由で失敗することを確かめる。
2. Green: テストが通る最小限の実装をし、全テストが通ることを確かめる。
3. Refactor: テストが通る状態を保ったまま、重複や分かりにくさを整理する。
4. 1 件ごとに次の形式で出して止まる。「次」と入力されたら、その 1 件をコミットしてから次のテストへ進む。

```markdown
## ストーリー 1/3: <ストーリー名>

### テスト 2/7: <テスト名>

- Red: <失敗の内容> [path/to/test:42](path/to/test:42)
- Green: <実装の要約> [path/to/file:42](path/to/file:42)
- Refactor: <整理の内容。なければ「なし」>
- 結果: 全 <件数> 件成功
```

進める中で新しく必要なテストに気づいたら、今のテストを終えてから一覧に加え、そのことを伝える。

このストーリーのテストを全て終えたら、次のストーリーのフェーズ 2 へ進む。全ストーリーを終えたら、フェーズ 5 へ進む。

## フェーズ 5: PR 作成

1. 全テスト、ビルド、リポジトリにある lint を実行し、通ることを確かめる。
2. PR のタイトルと本文の案を出して止まる。本文はリポジトリに PR テンプレートがあればそれに従い、なければ次を書く。
   - フェーズ 1 のユーザーストーリーと受け入れ条件
   - フェーズ 2 のコントラクトとスイムレーン
   - フェーズ 3 のテスト一覧
   - 実行した確認
3. 「次」と入力されたら作業ブランチを push し、既定ブランチ向けの PR を作る。利用者に指定がなければ、ドラフトにしない。
   - GitHub: `gh pr create --base <既定ブランチ> --title <タイトル> --body-file <本文のファイル>`
   - Azure DevOps: `az repos pr create --source-branch <作業ブランチ> --target-branch <既定ブランチ> --title <タイトル> --description <本文>`
4. 作成した PR の URL を報告する。
