# ミニ SDD

## 目的

実装を「何を作るか」「どう作るか」を利用者と合意してから進める。合意のないまま書いたコードは手戻りになるため、各フェーズの結果を利用者に確認してから次へ進む。

## 進め方

フェーズ 2 と 3 はユーザーストーリーごとに繰り返す。1 件のストーリーを設計から実装まで終えてから次のストーリーへ進むことで、前のストーリーで作ったコードを次の設計の前提にできる。

```text
フェーズ 0 → フェーズ 1
ユーザーストーリーごとに繰り返す
    フェーズ 2 → フェーズ 3
フェーズ 4
```

最初に workflow-base スキル（`../workflow-base/SKILL.md`）を読み込み、その共通ルールに従う。以下はこのスキル固有の手順である。

- フェーズ 0 と 1 の間は止まらない。フェーズ 1 でユーザーストーリーを書き起こしたところで最初に止まる。
- フェーズ 1 の FR の判定と、フェーズ 2 と 3 で出すのは、対象のユーザーストーリー 1 件分である。フェーズの見出しの次に、`## ストーリー 1/3: <ストーリー名>` のように対象のストーリーを示す。次に進む先も「ストーリー 2/3 のフェーズ 2: 設計」のようにストーリーを添えて書く。
- 答えが必要な質問として、フェーズ 0 の未コミット変更の扱いは、選択肢で聞いてよい。
- 後のフェーズで、合意済みのユーザーストーリー、機能要件、設計を変える必要が出たら、勝手に変えずに理由を示して確認する。

## フェーズ 0: チェックアウト

利用者に確認せず、次を進める。

1. 未コミットの変更があれば、作業を壊さないよう、何もせずに利用者へ扱いを聞いて止まる。
2. 既定ブランチを fetch し、最新の既定ブランチから作業ブランチを作って切り替える。ブランチ名はリポジトリの慣例に合わせ、慣例がなければ `feature/<依頼内容の短い英語名>` にする。
3. 依頼に関係するコード、テスト、issue やチケットを読み、現在の動きをつかむ。コードを読めば分かることを利用者に聞かないためである。

## フェーズ 1: 要件定義

ユーザーストーリーと機能要件（FR）は利用者が出し、AI は FR が十分かを観点表で判定する。AI が要件を作ると、利用者の意図とずれるためである。

### 1. ユーザーストーリーを書き起こす

利用者の「〇〇をやりたい」をユーザーストーリーの核とし、workflow-base のユーザーストーリーの書式で書き起こす。依頼文にないストーリーを AI から足さない。主体が依頼文から読み取れないときは、主体を「未定」と書いて利用者に聞く。

書き起こしに続けて、最初のストーリーの FR を思いつく限り挙げてもらって止まる。

```markdown
1. **<ストーリー名>**（<主体>）: <「にする」で結んだストーリー>
2. **<ストーリー名>**（<主体>）: <「にする」で結んだストーリー>

ストーリーや主体が違えば直してください。

## ストーリー 1/2: <ストーリー名>

このストーリーの FR を思いつく限り挙げてください。
```

### 2. FR が十分かを判定する

利用者が FR を挙げたら、次を行う。

1. 挙がった FR を、意味を変えずに「<条件>とき、システムは<振る舞い>する」の形に直す。
2. ストーリーの機能の種別を観点表（[references/viewpoints.md](references/viewpoints.md)）から選び、その種別の観点ごとに、対応する FR があるかを判定する。ストーリーが複数の種別にまたがるときは、全ての種別の観点を判定する。観点表のどの観点にも当たらない FR は、新しい観点の名前を付け、観点の列に「<観点>（表にない）」と書く。
3. テストで確かめられない FR は、具体さが足りない点を示す。

次の形式で出して止まる。足りない観点の FR は AI が作らず、利用者に挙げてもらう。

```markdown
## ストーリー 1/2: <ストーリー名>

機能の種別: <種別>

| FR | 観点 | 要件 |
|---|---|---|
| FR-1-1 | 応答性 | 検索ボタンを押したとき、システムは 1 秒以内に結果を表示する |
| FR-1-2 | 0 件や大量のとき | 該当がないとき、システムは「該当なし」と条件の見直し方を表示する |

足りない観点:

- <観点>: <この観点の FR がない、または具体さが足りない点>

足りない観点の FR を挙げるか、対象外と伝えてください。
```

全ての観点が FR か対象外で埋まるまで繰り返す。埋まったら、判定結果に続けて次のストーリーの FR を挙げてもらって止まる。

### 3. まとめる

全ストーリーの判定を終えたら、次の形式で全件を出して止まる。

```markdown
1. **<ストーリー名>**（<主体>）: <「にする」で結んだストーリー>

| FR | 観点 | 要件 |
|---|---|---|
| FR-1-1 | 応答性 | 検索ボタンを押したとき、システムは 1 秒以内に結果を表示する |

対象外: <対象外とした観点。なければこの行を書かない>
```

「次」と入力されたら、表にない観点を観点表へ追記してから、フェーズ 2 へ進む。

### 観点表を育てる

観点表（[references/viewpoints.md](references/viewpoints.md)）は、使うたびに育てていく部分である。表にない観点が採用されたら、次の手順で追記する。

1. この SKILL.md があるディレクトリの Git リポジトリで、既定ブランチを pull する。
2. 観点表の該当する種別の行に観点を追記する。当てはまる種別がなければ行を足す。
3. 観点表のファイルだけを、`mini-sdd の観点表に<観点>を追加` のようなメッセージでコミットし、既定ブランチへ push する。作業中のリポジトリのブランチには含めない。
4. リポジトリでない、未コミットの変更がある、push が拒否されたなどで反映できないときは、追記する内容を利用者に報告して、ワークフローを続ける。

## フェーズ 2: 設計

対象のユーザーストーリーについて、このストーリーの FR から次の 2 つを設計して止まる。前のストーリーで作ったクラスは前提として使う。

### コントラクト

ユーザーとの接点を決める。接点の種類に応じて、次を書く。

| 接点 | 書くこと |
|---|---|
| 画面 | 画面、操作、表示する内容、エラー時の表示 |
| API | メソッドとパス、リクエスト、レスポンス、エラー時の応答 |
| その他（CLI、イベント、ファイルなど） | 入力、出力、エラー時の動き |

### クラス設計

1. workflow-base のスイムレーンで処理の流れを描く。今回の変更部分は、このストーリーで変更する部分とする。
2. 図の下に、新規または変更するクラスを次の形式で並べる。既存の似たコードの構成と命名に合わせる。

```markdown
| クラス | 新規/変更 | 責務 | 公開メソッド | FR |
|---|---|---|---|---|
| OrderService | 変更 | 注文の確定を判断する | `Confirm(order)` | FR-1-1、FR-1-2 |
```

## フェーズ 3: TDD

最初に、対象のユーザーストーリーの単体テストの一覧を作る。

- このストーリーの全ての FR と、フェーズ 2 の公開メソッドの正常系と異常系を、いずれかのテストで確かめる。
- 実装しやすい順に並べる。単純なケースから始め、前のテストの実装を土台に次へ進めるようにするためである。
- テスト名はリポジトリの慣例に合わせる。

一覧の順に、1 件ずつ red、green、refactor を進める。テストごとには止まらず、このストーリーのテストを全て終えてから止まる。

1. Red: テストを 1 件だけ書いて実行し、期待どおりの理由で失敗することを確かめる。書いた時点で通るときは、前のテストの実装で満たせているため、Green と Refactor を飛ばす。
2. Green: テストが通る最小限の実装をし、全テストが通ることを確かめる。
3. Refactor: テストが通る状態を保ったまま、重複や分かりにくさを整理する。

進める中で新しく必要なテストに気づいたら、今のテストを終えてから一覧に加えて進める。テストを通せないときは、そこで止めて報告する。

全件を終えたら、次の形式で出して止まる。

```markdown
## ストーリー 1/3: <ストーリー名>

### テスト 1/7: <テスト名>

- 確かめること: <条件と期待する結果。対応する FR>
- Red: <失敗の内容。書いた時点で通ったら「最初から成功」> [path/to/test:42](path/to/test:42)
- Green: <実装の要約。飛ばしたら「なし」> [path/to/file:42](path/to/file:42)
- Refactor: <整理の内容。なければ「なし」>

### テスト 2/7: <テスト名>

...

結果: 全 <件数> 件成功
```

「次」と入力されたら、このストーリーの変更を 1 コミットにまとめ、次のストーリーのフェーズ 2 へ進む。全ストーリーを終えたら、フェーズ 4 へ進む。

## フェーズ 4: PR 作成

1. 全テスト、ビルド、リポジトリにある lint を実行し、通ることを確かめる。
2. PR のタイトルと本文の案を出して止まる。本文はリポジトリに PR テンプレートがあればそれに従い、なければ次を書く。
   - フェーズ 1 のユーザーストーリーと FR
   - フェーズ 2 のコントラクトとスイムレーン
   - フェーズ 3 で追加したテスト
   - 実行した確認
3. 「次」と入力されたら作業ブランチを push し、既定ブランチ向けの PR を作る。利用者に指定がなければ、ドラフトにしない。
   - GitHub: `gh pr create --base <既定ブランチ> --title <タイトル> --body-file <本文のファイル>`
   - Azure DevOps: `az repos pr create --source-branch <作業ブランチ> --target-branch <既定ブランチ> --title <タイトル> --description <本文>`
4. 作成した PR の URL を報告する。
