# Develop Feature Workflow

## 目的

Plan Modeで確定した計画を実装へ変換する。要件や設計の再整理は行わず、計画を前提に実装と検証を進める。

## 基本原則

- Plan Modeの計画を要件と設計の前提とし、実装中に矛盾する事実が見つかった場合は、実装を続けず計画の見直しが必要か確認する。
- 変更前に既存コード、テスト、リポジトリの指示を読み、既存の責務、命名、実装パターンに合わせる。
- 変更は要件を満たす最小単位にし、YAGNI、無関係なリファクタリング、先回りした汎用化を避ける。
- C#、ASP.NET Core、.NET の変更では `csharp-coding-rules` を参照する。
- 既存のバグを修正する場合は `debug-red-green` の手順を優先する。
- 検証できていないことを完了扱いしない。

## 1. 既存コードを理解する

- `AGENTS.md`、README、対象コード、関連テストを読む。
- 変更対象の責務、依存関係、テストの配置、既存のテストスタイルを確認する。
- 実装する振る舞いを、1回のTDDサイクルで扱える小さな単位に分ける。

## 2. TDDで実装する

機能実装は、次のサイクルを小さく繰り返す。

1. **Red**: production codeを変更する前に、期待する振る舞いを表す最小の自動テストを追加し、意図した理由で失敗することを確認する。
2. **Green**: Redテストを通すために必要な最小限のproduction codeを実装し、テストが成功することを確認する。
3. **Refactor**: Greenを維持したまま、重複、命名、責務分割を改善し、同じテストを再実行する。

アサーションを弱める、未検証の汎用実装を先回りして追加する、Greenを確認せず次のサイクルへ進むことは禁止する。TDDを適用できない生成コード、設定だけの変更、純粋な設計作業などでは、適用できない理由と代替検証を記録する。

## 3. 検証する

次の順で、変更範囲に必要な検証を行う。

1. 変更した振る舞いを直接見るテスト
2. 近傍の関連テスト
3. 必要に応じてlint、typecheck、build、analyzer

失敗した場合は、差分を広げる前に原因を確認する。実行できない検証は、理由と残リスクを明記する。

## 4. 完了を確認する

- Plan Modeの計画と要件を満たしている。
- 変更範囲外の挙動を変えていない。
- diffに無関係な変更、不要な汎用化、作業用コードがない。
- 実行した検証、未実施の検証、残リスクを報告できる。

## 最終報告

```text
Summary:
- 変更:
- TDD / 検証:
- 未実施の検証:
- 残リスク:
```
