# Agent Skills の更新

## 目的

スキルの更新依頼を、グローバルとプロジェクトの配置差分を確認したうえで一貫して反映する。

- グローバルのスキルは、GitHub の `taiseiishiyama00/agent-skills` を source of truth とする。
- プロジェクト固有のスキルは、対象リポジトリの `.agents/skills/` を正本とする。
- 同じ目的のスキルが両方にある場合は、片方だけを変更して内容を不一致のまま残さない。
- グローバルは `main` へ直接反映し、プロジェクトはブランチとドラフトPRでレビュー可能な状態にする。

## 発火例

- 「この内容をスキルに追記して」
- 「グローバルのスキルを更新して」
- 「プロジェクトとグローバルの同じスキルを修正して」
- 「この手順を Agent Skill にして、反映まで行って」

## 1. 対象と現在の配置を確認する

1. 依頼内容から、追加・修正する手順、対象スキル名、適用範囲を整理する。依頼文だけでは挙動が決まらない場合は、編集前に一つずつ確認する。
2. グローバルのローカルリポジトリを特定する。通常は `$HOME/repos/agent-skills` で、`$HOME/.agents/skills` のリンク先から解決してもよい。
3. グローバルリポジトリの `origin` が `taiseiishiyama00/agent-skills` であることを確認する。異なるリモートへ `main` を直接 push してはならない。
4. プロジェクトの Git ルートと、次のスキル配置を確認する。
   - 標準: `<repo>/.agents/skills/`
   - 互換確認: `<repo>/.github/skills/`、`<repo>/.claude/skills/`
5. 各配置から `SKILL.md` の `name`、目的、本文を読み、同じ `name` または明らかに同じ目的のスキルを重複候補として記録する。

## 2. 変更範囲を決める

- グローバルにしか存在しないスキルは、グローバルだけを更新する。
- プロジェクトに同じ `name` のスキルがある場合は、グローバルとプロジェクトの両方へ同じ依頼内容を反映する。プロジェクト固有の手順や例は保持し、共通部分だけを同期する。
- `name` は異なるが目的が重複している場合は、本文を比較して本当に同じ責務かを判断する。判断できない場合は推測で両方を変更せず、確認を求める。
- 同じ内容を別の配置へコピーして新しい重複を作ってはならない。既存配置を更新し、配置統一が別途依頼された場合だけ移動する。
- グローバルとプロジェクトの変更内容が異なる必要がある場合は、共通ルールとプロジェクト固有ルールを分けて記述する。
- 他のスキルを参照する場合は、参照先のスキル名またはパスだけを記載する。参照先のルールやチェック項目を列挙・要約して複製してはならない。参照先は今後拡張されるため、内容の重複は陳腐化の原因になる。

## 3. グローバルを `main` へ直接反映する

グローバルの変更は、`taiseiishiyama00/agent-skills` の `main` に直接反映する。GitHub 用のPRを作成して待つ運用にはしない。

1. グローバルリポジトリの `git status --short` を確認する。無関係な変更を削除、reset、上書き、commitに混在させてはならない。
2. 現在のチェックアウトが `main` でない、または作業ツリーが汚れている場合は、既存作業を壊さない一時 worktree を使って `origin/main` から作業する。同じスキルに未コミット変更がある場合は、勝手に統合せず確認する。
3. `origin/main` を fetch し、最新の `main` を起点に対象の `SKILL.md` を更新する。必要に応じて `agents/openai.yaml` とリポジトリのスキル一覧も更新する。
4. 次を確認する。
   - `SKILL.md` の `name` と親ディレクトリ名が一致している。
   - frontmatter と Markdown が正しい。
   - 手順が発火条件、実行手順、例外、完了条件まで具体化されている。
   - 依頼にないスキル、秘密情報、生成物、無関係な整形を含めていない。
   - `git diff --check` が成功する。
5. 日本語のコミットメッセージでコミットする。コミットには次の trailer を付ける。

   ```text
   Co-authored-by: Copilot <223556219+Copilot@users.noreply.github.com>
   ```

6. `git push origin HEAD:main` で直接反映する。force push や保護ルールの迂回はしない。push が拒否された場合は原因を報告し、PR作成へ勝手に切り替えない。
7. push 後に `origin/main` のコミットと変更内容を確認する。一時 worktree を使った場合は、変更がないことを確認してから後始末する。

## 4. プロジェクト側を更新してドラフトPRを作成する

プロジェクト側に重複候補がある場合は、グローバルの更新と同じ依頼内容をプロジェクトにも反映する。

1. プロジェクトの既定ブランチを最新化し、`fix/update-agent-skill-<skill-name>` などの作業ブランチを作る。既存のユーザー変更がある場合は保護し、対象ファイルと衝突するなら確認する。
2. 対象の `.agents/skills/<skill-name>/SKILL.md` を最小差分で更新する。プロジェクト固有の例、スクリプト、制約は削除しない。
3. 変更対象に応じた検証を実行する。少なくとも frontmatter、`name`、`git diff --check`、対象スクリプトや既存のスキル検証を確認する。
4. 日本語のコミットメッセージでコミットし、ブランチをリモートへ push する。
5. プロジェクトのホスティングサービスで、既定ブランチ向けの**ドラフトPR**を作成する。この環境の `ToBeRenamed` は Azure DevOps のため、Azure DevOps のPR機能を使い、GitHub用の操作へ置き換えない。
6. PR本文には、少なくとも次を日本語で記載する。
   - グローバルとプロジェクトの両方を更新した理由
   - TOBE / ASIS / GAP / 対応内容
   - 変更したスキルと配置
   - 実行した検証
   - グローバル側は `agent-skills` の `main` に直接反映済みであること
7. PR作成後に、source branch、target branch、draft状態、差分、検証結果を確認する。PRを自動で完了・mergeしてはならない。

## 5. 完了条件

- グローバルの対象変更が `taiseiishiyama00/agent-skills` の `main` に反映されている。
- 重複するプロジェクトスキルがある場合、両方の内容が依頼と整合している。
- プロジェクト側の変更がドラフトPRでレビュー可能になっている。
- 無関係な変更を巻き込んでいない。
- 変更、コミット、PR、検証結果を最終報告に記載している。
