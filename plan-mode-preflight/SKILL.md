# Plan Mode Preflight

## 目的

Plan Modeで計画をユーザーへ提示する前に、実装や変更を行わずに必要な事実を調査する。調査結果によって着地点が変わる状態で、調査そのものを実装計画のTo Doへ先送りしない。

このスキルはPlan Modeの前段調査と計画整理を担う。Plan Modeの承認前にproduction code、テスト、設定、依存関係、データを変更してはならない。方針確定後の実装は `develop-feature-workflow` または `debug-red-green` へ引き継ぐ。

## 適用範囲

次の依頼では、Plan Modeで計画を提示する前にこのスキルを適用する。

- Plan Modeで実装計画、修正計画、設計方針、To Doの作成を求める依頼
- 機能追加、既存機能変更、設定変更、障害、バグ、失敗テスト、回帰、実行時エラーの調査を伴う依頼
- 「原因を調査してから修正内容を計画して」「現状を確認して実装方針を決めて」のように、事前調査を明示した依頼

単純で調査対象が明確な依頼も、関連するファイルと指示を確認したうえで短い事前調査を完了させる。調査の深さは不確実性に合わせるが、調査を省略して推測だけで計画を作ってはならない。

## リードオンリー境界

事前調査中に許可されるのは、現在の状態を変えない読み取りと診断だけである。

- リポジトリ指示、README、対象コード、テスト、設定、依存関係、履歴、差分、ログを読む
- `git status`、`git log`、`git diff` などで状態と変更履歴を確認する
- 既存のテスト、再現コマンド、静的解析、診断コマンドを、ソース、設定、データ、外部サービスを変更しないことを確認したうえで実行する
- 失敗出力、スタックトレース、ログ、既存テストの観測事実を比較する

次の操作は禁止する。

- production code、テスト、設定、依存関係、ドキュメント、ブランチ、コミットを作成・編集・削除する
- formatter、生成ツール、migration、seed、fixture、データ更新、API呼び出しなど、書き込みを伴うコマンドを実行する
- パッケージをインストールまたは更新する
- 作業用ログ、dump、診断ファイルをリポジトリや一時領域へ作成する
- commit、push、PR作成、デプロイ、外部サービスや共有環境の状態変更を行う

テストや診断コマンドがキャッシュ、ビルド成果物、テストデータなどを書き込む可能性を確認できない場合は実行しない。実行できなかった理由と、調査結果への影響を計画に記載する。ユーザーの未コミット変更を上書き、退避、reset、checkoutしてはならない。

## 事前調査の手順

### 1. 依頼と制約を整理する

最初に、次を区別して記録する。

- 期待される状態、現在観測されている状態、対象範囲
- ユーザーが求める変更と、変更してはならない範囲
- 再現手順、エラーメッセージ、失敗テスト、ログなど、依頼に含まれる証拠
- 不足していてもリポジトリから確認できる情報と、ユーザーへ確認しないと進められない情報

情報不足だけを理由に調査を止めず、リポジトリから確認できる範囲を先に調べる。安全な調査を妨げる不足情報だけ、計画を確定する前に一つずつ確認する。

### 2. 現状と関連箇所を追跡する

作業ツリーの状態とリポジトリの指示を確認した後、依頼の振る舞いを入口から追跡する。

- `AGENTS.md`、README、対象ディレクトリの指示を読む
- エントリーポイント、呼び出し元、対象処理、データや設定の流れを読む
- 関連するunit / integration / UI test、テストデータ、fixtureを読む
- feature flag、環境変数、schema、依存関係、外部サービス境界を確認する
- 直近のコミット、関連差分、変更履歴、既知の制約を確認する

読んだファイルやシンボルは、原因と修正対象の根拠として計画に記録する。調査結果に関係しないコードまで広げない。

### 3. 再現と仮説検証を行う

可能なら最小の非破壊コマンドで挙動を再現する。コマンド、終了コード、主要な出力、再現性を記録し、既存テストで表現されているpublic behaviorを優先して確認する。

再現できない場合は、既存テスト、ログ、履歴、静的なコード追跡から確認できた事実と未確認の仮説を分ける。バグや障害では、必要に応じて2から4個の反証可能な仮説を置き、既存の観測だけで切り分けられる順に検証する。仮説を検証するためのコード変更や一時ログ追加は行わない。

### 4. 原因と修正方針を仮決定する

調査結果を次の形でまとめる。

- **事実**: コマンド、テスト、コード、設定、履歴、ログから直接確認できること
- **原因**: 期待値と実際の挙動を生んでいる欠陥または設計上の差分
- **根拠**: 原因を支持するファイル、シンボル、テスト、ログ、再現結果
- **影響範囲**: 影響を受ける振る舞い、経路、設定、利用者
- **修正方針**: 原因だけを直す最小の変更、対象箇所、維持する既存挙動
- **検証方針**: 追加・更新するテスト、再現手順、関連検証

修正候補が複数ある場合は、既存の責務、変更範囲、互換性、運用リスク、検証可能性を比較する。証拠から推奨案を仮決定できる場合はその理由と代替案を併記する。

## 不確実性の停止条件

次のいずれかに該当する場合、実装用To Doを確定してはならない。

- 原因を支持する証拠が不足し、複数の原因が残っている
- 再現できず、既存コード・テスト・ログからも原因を絞れない
- 修正候補のトレードオフが要件やユーザー判断に依存する
- 外部サービス、共有データ、権限、環境差分を安全に確認できない
- 非破壊の調査だけでは必要な事実を得られない
- ユーザーの未コミット変更や別の作業と対象範囲が衝突している

この場合は、断定せず、確認できた事実、試した調査、未確認事項、候補方針、ユーザーに求める判断を提示する。調査を実装To Doへ言い換えて計画を確定したり、根拠のない修正方針を一つに絞ったりしてはならない。

## 計画の出力形式

調査が完了し、方針を仮決定できた場合は、次の順で出力する。事前調査で完了した作業を、実装To Doへ重複して記載しない。

```text
# Plan

## 事前調査結果
- 期待される状態:
- 現在の状態:
- 確認した事実:
- 根拠:
- 影響範囲:

## 原因と修正方針
- 原因:
- 修正方針:
- 維持する既存挙動:
- 方針を選んだ理由:

## 実装 To Do
1. 対象ファイル・シンボルを変更する。
2. 必要なテストを追加または更新する。
3. 直接検証、関連検証、必要なlint / typecheck / buildを実行する。

## リスクと未決事項
- 残るリスク:
- ユーザー確認が必要な事項:
```

各To Doには、対象、変更内容、完了条件を含める。調査、原因特定、候補比較は「事前調査結果」または「原因と修正方針」に記載し、実装To Doには含めない。

方針を仮決定できない場合は、上記の「事前調査結果」に加えて、次の形式で止める。

```text
## 未確定事項
- 未確定の原因または方針:
- 追加で必要な証拠:
- 候補とトレードオフ:
- ユーザーに求める判断:

実装 To Do は、方針確定後に作成する。
```

## 後続ワークフローへの引き継ぎ

計画が承認された後の実装では、計画に記載した対象、根拠、テスト方針、制約を維持する。機能変更の実装と検証は `develop-feature-workflow`、バグ修正の再現・Red-Green-Refactorは `debug-red-green` を参照する。

実装中に計画と矛盾する事実が見つかった場合は、実装を続けず、事実と計画の差分を提示して再調査または方針確認へ戻る。

## 完了条件

- Plan Modeの計画を提示する前に、依頼に必要なread-only事前調査を完了している
- 事実、原因、根拠、影響範囲、修正方針、検証方針が区別されている
- 調査済みの内容が実装To Doへ重複していない
- 原因と方針が未確定の場合、実装To Doを確定せず判断を求めている
- 計画承認前にリポジトリ、データ、外部環境を変更していない
